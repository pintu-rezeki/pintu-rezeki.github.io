📘 Panduan tim · Wings Loyalty

Alur kerja Git yang benar
di project Wings.

Biar konsisten antar semua orang: setiap perubahan lewat jalur yang sama — branch sendiri, PR, lalu squash-merge. Tidak ada lagi commit langsung ke branch bersama.

⭐
Golden rule
Setiap perubahan → feat/ branch → Pull Request → squash-merge.
Tidak pernah commit atau git merge langsung ke main / uat / dev — sekecil apa pun.
Fondasi

Model branch

Tiga branch bersama (shared) yang tidak boleh disentuh langsung. Selalu pastikan base branch sebelum git checkout -b dan sebelum membuka PR.

main Production

Yang sudah live di production

Kode yang berjalan di user. Paling stabil, paling dijaga.

Jangan pernah buka PR fitur langsung ke main.
uat Stable test

Testing stabil + base untuk fix

Tempat QA/UAT. Fresh clone default ke sini. Basis untuk memperbaiki issue yang muncul di main/uat.

Fix issue main/uat → branch dari uat, PR ke uat.
dev Development

Fitur & pengembangan baru

Tempat fitur baru berkumpul sebelum dipromosikan. Bisa berisi hal yang belum tentu naik.

Fitur baru → branch dari dev, PR ke dev.
dev→ uat→ main
Arah promosi: pekerjaan naik bertahap dev → uat → main (lewat PR, bukan local merge).
Skenario A

Mengerjakan fitur baru

Titik awal: branch dari dev. Titik akhir: PR ke dev yang di-squash-merge.

✨

Feature flow

base: dev
  1. Mulai dari dev terbaru
    Pastikan base benar dan up-to-date sebelum bikin branch.
    # dari dalam repo service (mis. apps/backend)
git checkout dev
git pull origin dev
  2. Buat feat/ branch
    Nama deskriptif, selalu berprefiks feat/.
    git checkout -b feat/nama-fitur-singkat
  3. Kerjakan & commit di branch itu
    Commit sesering perlu — hanya di feat/ branch, bukan di dev.
    git add -A
git commit -m "feat: tambah fitur X"
  4. Push & buka Pull Request ke dev
    Rebase dulu ke dev terbaru bila sudah tertinggal, supaya squash bersih.
    git push -u origin feat/nama-fitur-singkat
gh pr create --base dev --title "feat: fitur X"
  5. Review → squash-merge lewat GitHub
    Setelah di-approve. Satu PR = satu commit rapi di dev.
    gh pr merge --squash --delete-branch
Skenario B

Memperbaiki issue di main / uat

Titik awal: branch dari uat (bukan dev). Titik akhir: PR ke uat, lalu dipromosikan.

🛠️

Fix / hotfix flow

base: uat
  1. Mulai dari uat terbaru
    Fix untuk issue di production/UAT selalu bercabang dari uat.
    git checkout uat
git pull origin uat
  2. Buat feat/ branch untuk fix
    Tetap prefiks feat/ (atau kesepakatan tim), branch tetap dari uat.
    git checkout -b feat/fix-nama-issue
  3. Perbaiki, commit, push
    Hanya di branch fix — jangan langsung di uat.
    git commit -am "fix: perbaiki issue Y"
git push -u origin feat/fix-nama-issue
  4. PR ke uat → squash-merge
    Setelah masuk uat dan terverifikasi, promosikan naik ke main lewat PR promosi.
    gh pr create --base uat --title "fix: issue Y"
gh pr merge --squash --delete-branch
Aturan main

4 aturan PR yang wajib

Ini yang menjaga history tetap rapi dan tim tetap sinkron.

🔀

Hanya lewat merged PR

Kode masuk ke shared branch hanya lewat PR yang di-merge di GitHub — bukan git push origin dev atau git merge lokal.

🥞

Squash-merge

Pakai opsi Squash (gh pr merge --squash). Satu PR jadi satu commit → history linear, mudah dibaca & di-revert.

🎯

Pastikan base branch

Sebelum checkout -b dan sebelum PR: fitur → dev, fix → uat. Salah base = kerja bisa naik terlalu cepat.

♻️

Rebase sebelum merge

Kalau base sudah maju, git rebase origin/<base> dulu supaya squash apply bersih tanpa konflik menumpuk.

Hindari

❌ Jangan begini

Pola-pola yang bikin flow tim jadi tidak konsisten. Tiap masalah ada padanan yang benarnya.

✕Commit langsung ke dev / uat / main (walau cuma satu baris).
✓Selalu bikin feat/ branch dulu, lalu PR — sekecil apa pun perubahannya.
✕Menggabung dengan git merge lokal lalu git push ke shared branch.
✓Integrasi hanya lewat PR di GitHub (gh pr merge --squash). Tidak ada local merge ke shared branch.
✕Merge commit / Merge branch 'uat'… yang mengotori history.
✓Squash-merge → satu commit rapi per PR, history tetap linear.
✕Buka PR fitur langsung ke main, atau branch fix dari dev.
✓Fitur → dari/ke dev. Fix issue main/uat → dari/ke uat. Promosi bertahap.
Pengingat harian

Cheat-sheet

Scan cepat sebelum mulai dan sebelum buka PR.

🚦 Sebelum mulai kerja

  • ✓Aku di repo service yang benar (apps/<repo>)?
  • ✓Base branch benar? Fitur = dev, fix = uat.
  • ✓git pull dulu supaya base terbaru.
  • ✓Bikin feat/<nama> — bukan kerja di shared branch.

🚀 Sebelum buka / merge PR

  • ✓PR target base yang benar (dev/uat, bukan main)?
  • ✓Sudah rebase ke base terbaru bila tertinggal?
  • ✓Merge pakai Squash, bukan merge commit / rebase-merge.
  • ✓Branch dihapus setelah merge (--delete-branch).
